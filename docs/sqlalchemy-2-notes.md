## 0. The big picture: ORM = two layers

SQLAlchemy splits cleanly into two layers. Knowing which layer you're in removes most confusion:

| Layer | What it does | Key objects |
|---|---|---|
| **Core** | Schema + SQL expression layer — tables, columns, SELECT/INSERT as Python objects | `Table`, `Column`, `select()`, `insert()` |
| **ORM** | Maps Python classes to tables; you work with objects, not rows | `declarative_base`, `Mapped`, `relationship()` |

In 2.0, both share one unified API style (typed, `select()`-first). There is **no legacy `Query` object** —
everything goes through `session.execute(select(...))`.

```
Python object  ──(ORM: session, mappers)──►  SQL expression  ──(Core: engine, connection)──►  PostgreSQL
```

## 1. What "2.0 style" means (the modern API)

Three non-negotiables of SQLAlchemy 2.0 style (all followed in this repo):

### 1.1 Annotated mappings: `Mapped[...]` + `mapped_column(...)`

**Old (1.x) style — names only:**
```python
class User(Base):
    id = Column(UUID, primary_key=True)        # type unknown to mypy
    name = Column(String(100), nullable=False)
```

**2.0 style — the type annotation is the source of truth:**
```python
class User(Base, TimestampMixin):
    id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), primary_key=True, server_default=sa.text("gen_random_uuid()")
    )
    phone: Mapped[str] = mapped_column(String(20), unique=True, nullable=False)
    email: Mapped[str | None] = mapped_column(String(255), unique=True)   # Optional → nullable
```

Rules the annotation drives:
- `Mapped[str]` → column is `NOT NULL` automatically
- `Mapped[str | None]` → column is `nullable=True` automatically
- The annotation is also what type checkers (mypy) and your IDE see on `user.phone`

### 1.2 `Mapped[type]` also declares relationships (see §4)

The **container shape of the annotation tells SQLAlchemy the cardinality**:
- `Mapped[list[Category]]` → "many" side
- `Mapped[ArtistKyc | None]` → "one" side (scalar)

### 1.3 `select()` statements, executed through the session

```python
# 2.0 idiom (this is what your *_service.py files do):
stmt = select(ArtistProfile).where(ArtistProfile.user_id == user_id)
profile = (await session.execute(stmt)).scalar_one()
```

## 2. Declarative mapping — how a class becomes a table

```python
# backend/app/shared/models.py
class Base(DeclarativeBase):      # 2.0: subclass DeclarativeBase (old: declarative_base() function)
    pass

class TimestampMixin:
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now(), onupdate=func.now()
    )

class ArtistProfile(Base, TimestampMixin):
    __tablename__ = "artist_profiles"
    ...
```

Key ingredients:
- **`DeclarativeBase`** — the registry. Every model inheriting from `Base` shares one metadata (`Base.metadata`), which is how Alembic sees all tables and how `relationship()` can resolve class names by string.
- **`__tablename__`** — the actual DB table name. The class name is irrelevant to the DB.
- **Mixins** — factor repeated columns (timestamps here) into a plain class; `Mapped` annotations in mixins work exactly like in the model.
- **Composite PK** — a model can have multiple `primary_key=True` columns. See `UserRoleGrant` (`user_id` + `role`) and the `artist_categories` junction table.

### Client default vs server default (important distinction)

```python
status: Mapped[ArtistStatus] = mapped_column(
    Enum(...),
    default=ArtistStatus.draft,          # CLIENT default: Python fills it before INSERT
    server_default=sa.text("'draft'"),   # SERVER default: Postgres fills it (DEFAULT clause)
    nullable=False,
)
id: Mapped[uuid.UUID] = mapped_column(
    UUID(as_uuid=True), primary_key=True,
    server_default=sa.text("gen_random_uuid()"),   # generated by Postgres, not Python
)
```

- `default=` → evaluated by SQLAlchemy in the Python process (a value or callable like `lambda: uuid4()`).
- `server_default=` → written into the DDL as `DEFAULT ...`; the DB generates it. Rows inserted by other tools still get it.
- If you `server_default` a column (like `id`), after `flush()` the object doesn't magically know the generated value — see `eager_defaults` below.

### `__mapper_args__ = {"eager_defaults": True}` — why this repo has it everywhere

```python
class ArtistProfile(Base, TimestampMixin):
    __mapper_args__ = {"eager_defaults": True}
```

After `INSERT`, SQLAlchemy normally leaves server-generated values **unloaded**, and reading `profile.created_at` later triggers a *lazy load* — which **crashes in async** with `MissingGreenlet`.

`eager_defaults=True` makes the INSERT use `... RETURNING created_at, status, ...` so all server defaults land on the object immediately. This is a core async-mapping technique.

## 3. The Session and the Unit of Work (async version)

### 3.1 Layered objects — don't confuse them

```
create_async_engine()   →  AsyncEngine      (connection pool to Postgres; one per app)
  └─ async_sessionmaker →  sessionmaker      (a factory for sessions)
       └─ AsyncSession  →  unit of work      (one per HTTP request, typically)
            └─ session.execute(stmt) → Result
```

- **Engine** = pool + dialect, thread-safe, expensive, created once.
- **Session** = identity map + change tracker. NOT a DB connection — it checks one out only during execute/flush.
- The `get_session` dependency in `app/shared/` yields an `AsyncSession` per request.

### 3.2 The identity map (the "aha!" concept)

Within one session, **one DB row = one Python object**, always:

```python
p1 = await session.get(ArtistProfile, some_id)
p2 = (await session.execute(select(ArtistProfile).where(...))).scalar_one()
p1 is p2   # True — same row, same object
```

Consequences:
- `session.get(Model, pk)` — pure PK lookup, hits the identity map first (may not emit SQL at all).
- Mutation is tracked on the *object*; you never write `UPDATE` by hand. This is the Unit of Work pattern.

### 3.3 Object states

| State | In session? | In DB? | How you got here |
|---|---|---|---|
| transient | yes (no) | no | `ArtistProfile(...)` |
| pending | yes | not yet | after `session.add(obj)` |
| **persistent** | yes | yes | after `flush()` / query — change tracking active |
| detached | no | yes | `session.close()`, or `expire_on_commit` fallout |

Only **persistent** objects sync to DB on flush. The typical service flow:

```python
profile = ArtistProfile(user_id=..., business_name=...)   # transient
session.add(profile)                                      # pending
await session.flush()                                     # INSERT sent; profile.id now populated; persistent
# ... maybe more changes ...
await session.commit()                                    # transaction ends (often done by the request dependency)
```

- **`flush()`** sends pending SQL *inside* the open transaction (needed to get PKs/FKs, to satisfy DB constraints, or to see rows in a later query in the same txn).
- **`commit()`** ends the transaction. After commit, all objects are **expired** by default — next attribute access re-selects them (in async this is a `MissingGreenlet` trap, which is why many apps set `expire_on_commit=False` in their sessionmaker).

### 3.4 The golden async rules

1. **Never lazy-load.** Any `relationship` without an eager strategy raises `MissingGreenlet` when accessed outside a greenlet context.
2. **Never `await` inside a sync callback that SQLAlchemy runs** (e.g. mapper events).
3. Everything is `await`: `execute`, `flush`, `commit`, `get`, `scalar_one`.

## 4. Relationships — where cardinality lives

**The core mental model:** relationships are *ORM-side sugar*. The database only knows foreign keys. A `relationship()` never creates a column — it just teaches SQLAlchemy how to join two classes it already knows via FKs.

```python
# DB truth (child side)              # Python navigation (parent side)
artist_id: Mapped[uuid.UUID] = ...   services: Mapped[list["ArtistServiceItem"]] = relationship(...)
    ForeignKey("artist_profiles.id")     lazy="selectin", cascade="all, delete-orphan"
```

SQLAlchemy infers **cardinality** from: FK position + FK uniqueness/PK-ness + the annotation shape (`list` vs scalar) + `secondary=`.

### 4.1 One-to-Many (1-N) — the workhorse

**DB:** FK column on the *many* side, no uniqueness.
**Python:** `Mapped[list[Child]]` on the *one* side.

```python
# backend/app/artist/models.py

# child — ArtistServiceItem
artist_id: Mapped[uuid.UUID] = mapped_column(
    UUID(as_uuid=True), ForeignKey("artist_profiles.id", ondelete="CASCADE"), nullable=False, index=True
)

# parent — ArtistProfile
services: Mapped[list["ArtistServiceItem"]] = relationship(
    lazy="selectin", order_by="ArtistServiceItem.sort_order", cascade="all, delete-orphan"
)
```

What's happening when you do `profile.services`:
- With `lazy="selectin"`: already loaded, it's just a Python list — no I/O.
- The list is a **dynamic collection** (`InstrumentedList`): appending/removing tracks changes; with `delete-orphan`, removal = DELETE.

Other 1-N examples in this repo:
- `User.role_grants` → `UserRoleGrant` (a user has many role rows)
- `ArtistProfile.photos` → `PortfolioPhoto`
- `Booking` references `user_id` / `artist_id` (FKs without a reverse `relationship` — that's legal; see §4.5)

### 4.2 Many-to-One — the scalar "other direction"

The mirror of 1-N: the child holds the FK, so navigating child → parent is always a **scalar**. You rarely declare it explicitly in this repo, but the canonical form:

```python
class ArtistServiceItem(Base):
    artist: Mapped[ArtistProfile] = relationship(back_populates="services")

class ArtistProfile(Base):
    services: Mapped[list[ArtistServiceItem]] = relationship(back_populates="artist")
```

**`back_populates` rule: declare it on BOTH sides or NEITHER.** One-sided `back_populates` = broken sync (the two sides stop mirroring each other in Python). This repo deliberately uses **one-directional relationships with no `back_populates`** (child → parent via raw FK columns instead) — simpler, less bookkeeping, and services always load from parent down.

Without `back_populates`, SQLAlchemy does NOT keep two Python objects in sync automatically:

```python
svc = ArtistServiceItem(artist_id=profile.id)   # sets the FK column
session.add(svc)
profile.services                                # won't contain svc until the relationship refreshes!
# vs. with a proper parent-side list append:
profile.services.append(svc)                     # artist_id filled in FOR YOU at flush
```

**Prefer mutating via the relationship** (`profile.services.append(x)`) — SQLAlchemy fills the FK automatically, you never write `x.artist_id = profile.id` by hand.

### 4.3 One-to-One (1-1) — two flavors

A 1-1 is just **a 1-N whose FK is uniquely constrained** — the ORM needs both the DB guarantee and `uselist=False`.

**Flavor A: FK + `unique=True`** (child table keeps its own PK):

```python
# ArtistProfile → User: one user, at most one artist profile
user_id: Mapped[uuid.UUID] = mapped_column(
    UUID(as_uuid=True), ForeignKey("users.id", ondelete="CASCADE"), unique=True, nullable=False
)
```

Parent side would look like:

```python
artist_profile: Mapped["ArtistProfile | None"] = relationship(uselist=False)
```

**Flavor B: FK **is** the primary key** (strongest — impossible to have two rows even by direct SQL):

```python
# backend/app/artist/models.py — ArtistKyc
class ArtistKyc(Base, TimestampMixin):
    artist_id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), ForeignKey("artist_profiles.id", ondelete="CASCADE"),
        primary_key=True          # ← PK = FK ⇒ strictly 1-1
    )

# parent side
kyc: Mapped["ArtistKyc | None"] = relationship(lazy="selectin", uselist=False, cascade="all, delete-orphan")
```

Markers of the 1-1 "one" side in Python:
- Annotation: `Mapped[Child | None]` — **scalar**, not `list`
- Keyword: `uselist=False` (without it, SQLAlchemy falls back to list-of-one behavior on some paths)
- `| None` because the relationship row may not exist yet (artist draft without KYC)

Why use a separate table instead of columns on `artist_profiles`? Here it's security-shaped: `aadhaar_encrypted` is a secret; keeping it in its own table means every normal `SELECT artist_profiles` can never accidentally ship it to a response — only code that explicitly joins `ArtistKyc` touches it.

### 4.4 Many-to-Many (N-N) — needs a junction table

Neither side can hold a FK (one column can't store N ids). Classical solution: a **junction/association table** with two FKs:

```python
# backend/app/artist/models.py — Core-level table (NOT a mapped class)
artist_categories = Table(
    "artist_categories",
    Base.metadata,                                   # ← registered in same metadata: Alembic creates it
    Column("artist_id", UUID(as_uuid=True),
           ForeignKey("artist_profiles.id", ondelete="CASCADE"), primary_key=True),
    Column("category_id", Integer,
           ForeignKey("categories.id"), primary_key=True),
)
```

Then `secondary=` on the relationship:

```python
class ArtistProfile(Base, TimestampMixin):
    categories: Mapped[list[Category]] = relationship(
        secondary=artist_categories, lazy="selectin", order_by=Category.sort_order
    )
```

Behavior you get:
- `profile.categories.append(cat)` → INSERT into `artist_categories` at flush (you never touch the Table directly)
- `profile.categories.remove(cat)` → DELETE the junction row (the `Category` itself survives)
- Composite PK on the junction ⇒ a pair can't be linked twice

### 4.5 N-N with extra columns → association *model* (the pattern `User ↔ roles` uses)

A plain junction table can't hold attributes (`granted_at`, who granted it, ...). So you promote the junction to a real ORM class and model it as **1-N + 1-N**:

```python
# backend/app/user/models.py
class UserRoleGrant(Base):
    __tablename__ = "user_roles"
    user_id: Mapped[uuid.UUID] = mapped_column(..., ForeignKey("users.id", ondelete="CASCADE"), primary_key=True)
    role: Mapped[UserRole] = mapped_column(user_role_enum, primary_key=True)   # enum column, not a text hack
    granted_at: Mapped[datetime] = mapped_column(..., server_default=func.now())

class User(Base, TimestampMixin):
    role_grants: Mapped[list["UserRoleGrant"]] = relationship(lazy="selectin", cascade="all, delete-orphan")

    @property
    def roles(self) -> set[UserRole]:                    # convenient set view over the rows
        return {g.role for g in self.role_grants}

    def grant(self, role: UserRole) -> None:             # domain behavior lives on the model
        if role not in self.roles:
            self.role_grants.append(UserRoleGrant(role=role))
```

Decision rule:
- Junction truly carries **no data** → `Table` + `secondary=` (artist ↔ categories)
- Link needs **attributes/behavior** → association model + 1-N (user ↔ roles)

### 4.6 FK placement cheat sheet (recap)

| Cardinality | Where FK lives | DB constraint | Python annotation | Extra keywords |
|---|---|---|---|---|
| 1-N | child table | plain column, `index=True` | `Mapped[list[Child]]` | `cascade="all, delete-orphan"` |
| N-1 | child table (same FK) | — | `Mapped[Parent]` (scalar) | `back_populates` on both sides if used |
| 1-1 | child table | `unique=True`, or FK = PK | `Mapped[Child \| None]` | `uselist=False` |
| N-N | junction table, 2 FKs | composite PK | `Mapped[list[X]]` | `secondary=junction` |
| N-N + attrs | association model | composite/own PK | `Mapped[list[Assoc]]` | model as two 1-Ns |

## 5. Loading strategies (`lazy=`) — the async survival chapter

Because async sessions **cannot** emit SQL mid-attribute-access (no greenlet to wait on), you must declare how each relationship gets loaded:

| `lazy=` | What it does | SQL cost | Verdict in async |
|---|---|---|---|
| `"select"` (default) | lazy-load on first access | 1 per row | ❌ **raises `MissingGreenlet`** — never rely on default |
| `"selectin"` | parent query, then one extra `SELECT ... WHERE fk IN (:ids)` automatically | 2 queries total | ✅ default choice in this repo |
| `"joined"` | `LEFT OUTER JOIN` in the same statement | 1 query, row duplication | ✅ for 1-1 / few-child, avoid for large 1-N |
| `"raise"` / `"raise_on_identity"` | touching an unloaded rel = instant error | — | ✅ strict mode to catch missed eager loads |
| `noload` | don't load, don't error — silent empty | — | ⚠️ dangerous (silent emptiness) |

**`selectin` vs `subquery`:** `subquery` (legacy) always runs the join even when unneeded; `selectin` only fires for collections being loaded and batches ids — prefer `selectin` in 2.0 (and it's async-safe, unlike some `subquery` paths).

Per-query override with loader options (when a service needs a different shape):

```python
from sqlalchemy.orm import joinedload, selectinload

# eager-load photos + kyc for one profile, deep for a 3-level graph
stmt = (
    select(ArtistProfile)
    .where(ArtistProfile.id == pid)
    .options(
        selectinload(ArtistProfile.services).joinedload(ArtistServiceItem.template),
        selectinload(ArtistProfile.photos),
    )
)
```

Note: **relationship-level `lazy="selectin"` is a *default*, not a mandate** — a query can override it with `.options(lazyload(...))` / `raiseload(...)` when it doesn't want the children.

Why this repo chose `lazy="selectin"` at the mapper level (see comment in models):
> "async sessions can't lazy-load, and every read of a profile needs all three."

i.e. the response serializers *always* touch children → put the decision where the knowledge is, instead of repeating `.options(...)` in every service function.

## 6. Querying — 2.0 style

### 6.1 The statement → execute → result pipeline

```python
from sqlalchemy import select, func

stmt = select(ArtistProfile).where(ArtistProfile.status == ArtistStatus.approved)
result = await session.execute(stmt)        # Result object
profiles = result.scalars().all()           # rows → list[ArtistProfile]
```

Result-extraction vocabulary (memorize these five):

| Call | Use when | Raises if |
|---|---|---|
| `.scalars().all()` | list of ORM objects | — |
| `.scalar_one()` | exactly one row expected (PK lookups) | 0 rows or ≥2 rows |
| `.scalar_one_or_none()` | one row or none | ≥2 rows |
| `.first()` | maybe-none, tolerate extra | never |
| `.all()` (no scalars) | tuples of multiple columns | — |

### 6.2 Joins across relationships

Two ways — via FK columns explicitly, or via relationship traversal:

```python
# relationship traversal (needs the relationship declared)
stmt = select(Booking).join(Booking.artist)          # join through artist_id FK

# explicit ON
stmt = select(Booking).join(ArtistProfile, Booking.artist_id == ArtistProfile.id)

# filter through a 1-N with EXISTS (the pattern for "artists having a service in category X")
stmt = select(ArtistProfile).where(
    sa.exists().where(ArtistServiceItem.artist_id == ArtistProfile.id,
                      ArtistServiceItem.category_id == cat_id)
)
```

### 6.3 Aggregates & grouping (Core functions work in `select`)

```python
stmt = (
    select(Booking.artist_id, func.count(), func.avg(Booking.amount_paise))
    .group_by(Booking.artist_id)
)
rows = (await session.execute(stmt)).all()   # list of named tuples
```

## 7. Constraints & DDL — what the ORM does NOT do

- **`relationship()` adds no column.** Only `mapped_column(..., ForeignKey(...))` and `__table_args__` change the DDL.
- Schema changes = **Alembic migrations** (`backend/alembic/`), never "the model changed so the DB changed". The models are the *spec*, Alembic is the *application* of the spec.
- Repo uses DB-level protection in layers (defense in depth):
  - `ForeignKey(..., ondelete="CASCADE")` — DB deletes children even if ORM cascade is forgotten
  - `sa.CheckConstraint("price_paise > 0")` — data invariants the DB itself enforces (see `ArtistServiceItem.__table_args__`)
  - `unique=True` — uniqueness (user_id on ArtistProfile, phone on User)
  - `index=True` — query performance on FK columns you filter by
- `Enum(ArtistStatus, name="artist_status", values_callable=...)` — Postgres native enum type; `values_callable` makes SQLAlchemy store the enum's **`.value`** strings instead of Python member names.

## 8. Common pitfalls (async + 2.0 specific)

1. **`MissingGreenlet`** on any lazy-load or server-default access in async → fix with `lazy="selectin"`/`joined` upfront, or `eager_defaults=True`.
2. **Forgetting `await`** on `session.execute/flush/commit` — returns coroutine, silently does nothing until awaited.
3. **`session.get()` vs `select()`**: `get` is PK-only; for anything else use `execute(select(...))`.
4. **Mutating FK columns instead of relationships**: `profile.services.append(x)` fills `artist_id` for you; setting `x.artist_id` directly leaves stale parent-side lists within the same session (only refreshed on next query/expire).
5. **`delete-orphan` without `save-update`** — the modern full form is `cascade="all, delete-orphan"`; `delete-orphan` alone means "removed from collection ⇒ DELETE", which is what you want for owned children (services/photos/kyc) but **not** for shared rows (never use it on the `categories` N-N — deleting an artist must not delete a `Category`).
6. **Expiring after commit**: touching attributes post-commit triggers a refresh SELECT (sync) or an error (async); hence `expire_on_commit=False` in most async setups.
7. **One-directional relationships are fine** — but then child→parent navigation must use the FK *column* (`svc.artist_id`), not an object attribute that doesn't exist.
8. **N-N `remove()` deletes the link, not the row** — that's correct behavior, but easy to misread: `profile.categories.remove(cat)` keeps `cat` alive.

## 9. One-page cheat sheet

```
MAPPING          class(Base, Mixin) + __tablename__ + Mapped[...]/mapped_column(...)
NULLABILITY      Mapped[X] → NOT NULL · Mapped[X | None] → NULL
SERVER VALUES    server_default=sa.text(...) + __mapper_args__ eager_defaults (async!)
1-N              FK in child + Mapped[list[Child]] + cascade="all, delete-orphan"
1-1              FK unique / FK-as-PK + Mapped[Child | None] + uselist=False
N-N              Table(junction, 2 FKs, composite PK) + relationship(secondary=...)
N-N + attrs      association model ⇒ two 1-Ns (User ↔ UserRoleGrant)
LOADING (async)  lazy="selectin" (collections) / "joined" (1-1) / never default "select"
OVERRIDES        .options(selectinload(M.rel).joinedload(M.rel2))
QUERYING         select().where() → await session.execute() → .scalars()/.scalar_one()
WRITING          session.add → await flush (gets PKs) → commit (usually by dependency)
DDL              models ≠ migrations — Alembic applies changes; FK/Check/Unique live in DB
```

## 11. Myth-busting: "1.x did it with N extra files/lines, 2.0 doesn't?"

Common belief: *"In 1.x we made an association.py + model for N-N, and wrote a relationship line in BOTH models for 1-N — but 2.0 removed all that."* Both halves are misconceptions. **2.0 changed the language (types, queries, async), not the relational algebra.**

### Myth 1: "N-N needed an association model file in 1.x, gone in 2.0"

The rule is identical in **both versions** — it depends on whether the **link carries data**, not on the version:

**Case A — link has no extra columns → plain `Table` + `secondary=`.** You cannot escape a third table; an N-N relationship is physically impossible without one, and SQLAlchemy must be told about it somewhere. This repo's `artist_categories` (2.0 code!) is exactly the 1.x-style Core `Table`:

```python
artist_categories = Table(          # NOT a class — still required in 2.0
    "artist_categories", Base.metadata,
    Column("artist_id", ..., ForeignKey("artist_profiles.id"), primary_key=True),
    Column("category_id", ..., ForeignKey("categories.id"), primary_key=True),
)
categories: Mapped[list[Category]] = relationship(secondary=artist_categories, ...)
```

**Case B — link has attributes (`granted_at`, ...) → association model (a real mapped class).** Alive and well in 2.0 — it's literally `UserRoleGrant` in this repo, and the whole thing degrades to **two 1-Ns** (composite PK `user_id + role` + `granted_at`).

So the only genuine 2.0-era shift is stylistic: `Mapped[...]` typing makes the two-1-Ns pattern cleaner than the old `secondary` + association-object hybrid, so many teams skip `secondary=` whenever the link has *any* attributes.

### Myth 2: "1-N required a relationship line in both models in 1.x"

Never mandatory — in 1.x or 2.0. There have always been **three legal choices**:

| Choice | Lines written | Works in 1.x? | Works in 2.0? | Used in this repo? |
|---|---|---|---|---|
| **Unidirectional** — relationship only on parent; child navigates up via raw FK column (`svc.artist_id`) | 1 | ✅ | ✅ | ✅ (`services`, `photos`, `kyc`, `role_grants`) |
| **Bidirectional** — `back_populates` on both sides | 2 | ✅ | ✅ (preferred) | ✗ (not needed) |
| **`backref=`** — one line magically creates the reverse attribute | 1 | ✅ (idiomatic) | ⚠️ legal but discouraged | ✗ |

Why `backref` fell out of favor in typed 2.0 code: it generates an attribute on the *other* class that **doesn't appear in that class's annotations** — mypy can't see `ArtistServiceItem.artist`, and the reader of the child model can't either. 2.0's philosophy is "everything visible in the type annotations", so the community settled on: either **one honest unidirectional line**, or **two honest `back_populates` lines**.

### The real 1.x → 2.0 diff table

| Concern | 1.x style | 2.0 style | Changed? |
|---|---|---|---|
| N-N junction | `Table` + `secondary=` | same | ❌ no |
| N-N with data | association class | same (`UserRoleGrant`) | ❌ no |
| 1-N unidirectional | allowed | allowed (repo's choice) | ❌ no |
| 1-N bidirectional | `backref` or `back_populates` | `back_populates` preferred | ⚠️ style shift only |
| Column mapping | `Column(...)` by name | `Mapped[X]` + `mapped_column(...)` | ✅ yes |
| Nullability | explicit `nullable=` | derived from `X` vs `X \| None` | ✅ yes |
| Querying | `session.query(X).filter(...)` | `await session.execute(select(X).where(...))` | ✅ yes |
| Async | afterthought (greenlet hacks) | first-class (`selectin`, `eager_defaults`, `AsyncSession`) | ✅ yes |

**One-sentence takeaway:** junction tables and both-sided relationship lines are still exactly what you write *when the design calls for them* — 2.0 just made the types explicit, killed `session.query()`, and made async the default mental model.
